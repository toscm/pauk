Chapter One

What pauk Is

A flashcard trainer whose single source of truth is an HTTP API. Every interface — the terminal app today, a web or mobile app later — is a thin client of that one contract.

pauk stores questions and answers, organises them into a graph of decks, and quizzes you on them. Questions are written in Markdown and may embed images. The name is short, verb-able, and thematically earned the way git is: it comes from the German pauken, “to cram”.

The governing decision is that the API is the product. The database is touched by nothing but the API; the CLI, and any future web or mobile client, speak only HTTP. That keeps the clients disposable and the contract durable — the implementation language (PHP, chosen because it runs on already-paid shared hosting) is an implementation detail behind the spec.

The three components

The repository is a monorepo with three roles, named by what they are, never by their language:

  • api/ — the HTTP API. PHP 8.4 on the Slim 4 framework, talking to MariaDB through PDO.
  • cli/ — the command-line client. Python, built on Textual for the full-screen app and Typer for the scripting subcommands.
  • content/ — importable decks of cards (Italian, German geography, the Greek alphabet) as JSON.
Design principle

As simple as possible, and conventional wherever a convention exists — so the code and the app feel familiar from the first minute. One database engine everywhere. One organising concept (directories) instead of two (directories and tags).

Chapter Two

The Data Model

Fourteen tables in MariaDB. Everything owned by a user carries user_id from the first migration; decks form a directed acyclic graph, not a tree; leaderboards are per question count.

Decks are a graph, not a folder tree

A directory is a collection, not a filesystem node. A card can belong to any number of directories; a directory can sit under any number of parents. So “Italian core verbs” is both a quiz of its own and a sub-deck of “Italian verbs” — and quizzing the parent includes the child transitively.

The graph is stored as two edge tables. Cycles are rejected when an edge is created; a name is unique among its siblings, so a slash-path like italian/verbs/core-verbs resolves unambiguously even though a deck may be reachable by several paths. Deleting a directory never deletes a card — an unreferenced card simply becomes unfiled.

Traversal gotcha

Single-deck traversal uses a recursive CTE. MariaDB infers the CTE column type from the anchor row, and a bare bound parameter is typed as a short string that silently truncates larger ids — so the anchor is always written SELECT CAST(? AS UNSIGNED). The deck picker, which needs every directory’s transitive card count at once, instead loads all edges in a few queries and computes the closures in PHP; one CTE per directory would be an N+1 against the remote database.

History and scores

Every answer is appended to reviews — the append-only log the weighted question-picker reads, and the seam where real spaced repetition can slot in later. Three run tables record finished sessions and drive the leaderboards.

ColumnTypeTable & notes

Why leaderboards are per question count

A “best run” only means something against a fixed length. Scoring 5/5 on a five-card quiz is not comparable to 18/20 on a twenty-card one, so each (deck, total) keeps its own top-three. Repeat and repeat-wrong runs are marked ranked = 0 so a one-question practice pass can never masquerade as a record — and abandoning a quiz early finishes the run unranked for the same reason.

Chapter Three

Five Kinds of Card

The same deck can mix all five. Grading and question-selection are server-side, so every client behaves identically; where a task needs a model, only the client talks to it.

mc Multiple choice

Correct when the chosen set of option ids equals the correct set. Several options may be correct.

Q  Which definite article is correct?  ___ zaino (backpack)
   ▣ lo   □ il   □ la   □ l’

text Free text

Normalised (case-folded, diacritics and punctuation stripped), then matched. Typos within a length-scaled Levenshtein budget are accepted and flagged; answers under four characters must match exactly.

Q  Translate to Italian: to be
A  essere        # “essre” → accepted (typo), “avere” → wrong

match Matching

Connect each left item to its right. Ideal for conjugation tables. In quiz form the right side is shuffled; a left matches the choice sharing its row id, so the correct pairing never leaks.

Q  Match each pronoun to the present tense of essere (to be)
   io → sono    tu → sei    lui/lei → è
   noi → siamo  voi → siete

quest LLM dialog task

A scenario you solve by conversation with a model playing a role, judged for success, scored by fewest messages. The dialog and the judgement run entirely in the client; the API only stores the definition and records the run.

scenario  You are at a bakery in Rome. Order 2 cornetti and
          1 caffè. The baker speaks only Italian.
role      A warm Italian baker who speaks ONLY Italian…
success   The customer clearly asked, in Italian, for 2
          cornetti and 1 caffè.
budget    8 messages

route Map navigation task

Navigate a graph from a start to a goal by picking edges — multiple choice, never free typing. Kilometres are summed deterministically from a bundled graph, never trusted to a model; the highscore is the fewest kilometres.

Q  Drive from München to Berlin using as few km as possible.
   graph germany-autobahn   optimum 595 km (Dijkstra)

How the next question is chosen

Selection is server-side too, so all clients quiz identically. Cards are drawn by weighted sampling that favours the new, the often-wrong, and the long-unseen:

# from the reviews log, per candidate card
error_rate = (wrong + 1) / (asked + 2)      # Laplace-smoothed
staleness  = 1 if never asked else min(days, 30) / 30
weight     = error_rate × (1 + staleness)

A brand-new card gets the maximum weight; a card answered right and seen yesterday sinks toward the floor. This is deliberately not a full Leitner or SM-2 scheduler — the endpoint is simply the place where one could later be dropped in.

Chapter Four

Deployment on IONOS

The API runs on rented IONOS shared hosting — no root, no daemons, PHP invoked per request by Apache. Getting a clean REST API to behave there took a handful of specific accommodations.

The host serves PHP out of ~/web/pauk and offers a managed MariaDB (2 GB) reachable only from the webspace. There is no way to run a long-lived process, which is exactly why the API is PHP and not a Python or Go daemon: on this box, PHP-per-request is the only server model available.

Layout on the server

Only the front controller and uploaded media sit in the docroot; the application code, its vendored libraries, and the credentials live outside it, so they can never be served as text.

~/ on the IONOS webspace
PathRole
web/pauk/docroot — a tiny index.php stub + media/
pauk-app/application code + vendor/, not web-reachable
pauk.envDB credentials, mode 600, never in git
pauk-backups/nightly dumps + the prune script

The docroot stub simply points the real front controller at the app directory and the credentials file:

// ~/web/pauk/index.php
putenv('PAUK_APP_DIR=…/pauk-app');
putenv('PAUK_ENV_FILE=…/pauk.env');
require '…/pauk-app/public/index.php';

Two Apache quirks, and their fixes

Quirk 1 — mod_rewrite 500s

This Apache returns a 500 on a per-directory RewriteRule. The router uses FallbackResource /index.php instead, which routes every not-a-real-file request to the front controller and still lets Apache serve media/ directly.

Quirk 2 — the Authorization header vanishes

CGI PHP drops the Authorization header, so bearer tokens never arrive. A SetEnvIf in .htaccess re-exposes it, and the front controller promotes the REDIRECT_-prefixed variants that the FallbackResource internal redirect produces. Remove either and every authenticated endpoint 401s — in production only; the local dev server has neither quirk.

Deploying

make deploy is the only path to production. It runs the full test suite and aborts on any failure; refuses a dirty or unpushed tree; builds vendor/ with --no-dev; takes a database dump before migrating; rsyncs the app (keeping the previous version as .prev for make rollback); runs forward-only migrations; and finishes with a smoke test that the live /health returns the just-deployed version.

Backups

A nightly cron dumps and gzips the database, then prunes on a date-anchored grandfather-father-son schedule computable from filenames alone: keep everything from the last 7 days; keep the 1st, 8th, 15th and 22nd for 35 days; keep every 1st for a year. About twenty small dumps at any time. Media files are content-hashed and immutable, so a weekly rsync of media/ is enough.

TLS

The domain pauk.aao756.de is covered by the hosting contract’s wildcard certificate (*.aao756.de, auto-renewed), so a single certificate secures the app and every future subdomain at no extra cost.

Chapter Five

The Terminal Client

Run pauk with no arguments and you are inside a full-screen application. Network calls happen on background threads, so the UI never blocks; status bars carry only the non-obvious keys.

You authenticate once — pauk login https://pauk.aao756.de stores a token in ~/.config/pauk/config.toml — and every scripting subcommand (import, stats, media, quiz --dir) remains available for automation. What follows is the interactive path.

Chapter Six

The HTTP API

Base URL https://pauk.aao756.de/api/v1. JSON in and out; a bearer token on every endpoint but /health. Errors are always {"error":{"code","message"}} with a matching status.

The examples below are runnable; export your token first.

export TOK=57db…855b1
export API=https://pauk.aao756.de/api/v1

Health — the only unauthenticated route

curl "$API/health"
→ {"status":"ok","db":"ok","version":"0.7.0"}

Create a card

curl -X POST "$API/cards" -H "Authorization: Bearer $TOK" \
  -H "Content-Type: application/json" -d '{
    "type": "text",
    "question_md": "Translate to Italian: **to be**",
    "accepted_answers": ["essere"],
    "dirs": [12]
  }'

List & filter cards

# every match card under a deck, transitively
curl -G "$API/cards" -H "Authorization: Bearer $TOK" \
  --data-urlencode "dir=12" -d "recursive=1" -d "type=match"

Answer a card — grading is server-side

curl -X POST "$API/cards/42/answer" -H "Authorization: Bearer $TOK" \
  -H "Content-Type: application/json" -d '{"answer":"essre"}'
→ {"correct":true,"match":"typo",
     "expected":{"accepted_answers":["essere"]}}

Start & finish a quiz run

curl -X POST "$API/quiz/runs" -H "Authorization: Bearer $TOK" \
  -H "Content-Type: application/json" -d '{"dir_id":12,"total":20}'
→ {"id":7,"best":{"correct":18,"total":20,"accuracy":0.9}}

curl -X PATCH "$API/quiz/runs/7" -H "Authorization: Bearer $TOK" \
  -H "Content-Type: application/json" -d '{"correct":19,"total":20}'
→ {"rank":1,"top":[{"accuracy":0.95,"correct":19,"total":20,…}]}

Record a quest or route outcome

curl -X POST "$API/cards/30/quest-run" -H "Authorization: Bearer $TOK" \
  -d '{"success":true,"messages_used":6}'
→ {"best_messages":6,"rank":1,…}

curl -X POST "$API/cards/31/route-run" -H "Authorization: Bearer $TOK" \
  -d '{"success":true,"km":595}'
→ {"best_km":595,"rank":1,…}

Directories & the quiz picker

# resolve a slash-path to a directory
curl -G "$API/dirs/resolve" -H "Authorization: Bearer $TOK" \
  --data-urlencode "path=italian/verbs/core-verbs"

# the flat, popularity-sorted picker listing (batched, fast)
curl "$API/quiz/dirs" -H "Authorization: Bearer $TOK"

Upload media

curl -X POST "$API/media" -H "Authorization: Bearer $TOK" \
  -F "file=@map.png"
→ {"url":"https://pauk.aao756.de/media/<sha256>.png", …}

The returned URL goes straight into a card’s Markdown as ![map](…). Content imported from JSON can reference a not-yet-uploaded file as media:maps/de-bayern.png; pauk import uploads it and substitutes the URL, deduplicating by content hash.
